# Takewise v1 design

Status: revised after council rounds 1 (Claude Fable 5.2: 6/10, GPT Sol 6.2: 7/10) and 2 (8.5/10, 8/10), 2026-11-22.

## Why

Narrating the 51-second Kindred promo in DaVinci Resolve took longer than the narration itself. The track would not arm until the mic was patched in a non-scriptable dialog, Resolve played the voice back with a delay ("super irritating"), the script lived in marker notes nobody could read while speaking, and an agent then had to hunt down the takes and transcribe them to find out whether the words were right.

Takewise is a small macOS app for exactly that job: speak a script over a finished film, line by line, retake what went wrong, and hand the chosen takes to an agent and to Resolve. The main win is the agent interface. Agents write the script, read every take's verdict, add their own judgments, and place the result in Resolve; the human gets one focused screen for speaking.

## Goals

- Record narration over a film with the line to read shown large, timed to the picture.
- Record any number of takes per line; never lose a take.
- After every take, say within seconds whether it is good enough: wrong or missing words, overrun of the line's slot, clipping or silence, each with a reason.
- Rank the takes of a line and propose one; the narrator commits a choice with one key.
- Let the narrator fix a line's wording in place and set a line's start by pressing a key while the film plays.
- Expose everything to agents through a plain folder format and a CLI with JSON output, including a way for an agent to add its own judgment of a take.
- Export one narration WAV aligned to the film's first frame, plus a manifest of exact sample positions.

## Non-goals for v1

- A script editor beyond fixing a line's text and setting its start. Agents write `script.toml`.
- Waveform editing, mixing, multiple voices or tracks. (Export cleanup, below, is a fixed processing profile, not an effects rack.)
- Splicing single words into a take. Retakes replace whole lines; long lines are split into two.
- Judging delivery with an audio model inside Takewise. Agents do that from outside and record it with `takewise judge`.
- Retiming the film to the voice. The manifest gives agents the measured timings to do that.
- Driving Resolve from Takewise. Agents place the export in Resolve with their own Resolve tools.
- Hearing the previous line's take during pre-roll (later).
- Loudness control beyond the fixed `clean` export profile (one gain and a look-ahead peak limiter to −16 LUFS, true peak at most −1 dBTP).
- Windows and Linux. Apple Silicon macOS only.

## Anti-goals

- Becoming a DAW. Takewise ends at chosen takes plus timings.
- Anything choosing a take on its own. Checks and judgments flag and rank; only the narrator (Enter) or an explicit `takewise choose` commits a choice.
- Monitoring the narrator's voice without being asked. Monitoring is off until the narrator turns it on (changed 2026-11-23, see "Setup and sound").
- Needing Resolve, a network connection or a cloud account to record and check.

## Approaches

| Approach | Trade-off |
| --- | --- |
| Swift app (AppKit) with AVFoundation | Easiest media path (AVPlayerView, AVAudioEngine). A second language beside the Rust CLI; Niklas has had trouble with SwiftUI and AppKit is verbose. |
| **Rust with GPUI and gpui-kit, AVFoundation through objc2** (chosen) | One language for app, CLI and checks; same stack as Focal, which Niklas already ships. Video inside a GPUI window is unproven, so a spike comes first. |
| Tauri or a web page | Fast UI, but browser capture adds processing and unclear latency, and playback sync is harder to trust. |

Niklas chose GPUI with gpui-kit on 2026-11-22, with the middle ground for script editing (agent drafts, app fixes text and sets starts).

## Project folder

A project is a directory, by convention `<name>.takewise/`:

```text
kindred-promo.takewise/
  project.toml        # film, audio settings, check settings
  script.toml         # the lines, edited by agents and by the app
  takes/<line-id>/001.wav
  takes/<line-id>/001.json  # the take's recording metadata, written before the WAV is published
  takes/.passages/<uuid>.wav   # a passage: several lines recorded in one go, kept whole
  takes/.passages/<uuid>.json  # its sidecar: the lines, the placement and the cuts
  takes.jsonl         # append-only ledger
  .lock               # advisory lock held while writing
  export/narration.wav  # or .flac, see "Setup and sound"
  export/manifest.json
```

`project.toml`:

```toml
format = 1
film = "../renders/kindred-promo-v2.mp4"   # relative to the project dir, or absolute
sample_rate = 48000

[film_info]                                 # written by init (ffprobe), and by `takewise film` (or `status --refresh-film`)
duration_s = 51.5
size = 12345678
modified = "2026-11-22T20:05:11Z"

[previous_film]                             # optional: the render `takewise film` replaced last
film = "../renders/kindred-promo-v1.mp4"   # as `film` held it
duration_s = 52.0
size = 12000000
modified = "2026-11-21T18:30:02Z"
replaced_at = "2026-11-22T20:06:40Z"

[input]
device = "RODECaster Duo Main Stereo"      # matched by name; `takewise doctor` lists devices
channel = 1                                 # 1-based input channel, recorded as mono
latency_offset_ms = 0                       # manual correction from the loopback test

[record]
preroll_s = 3.0                             # 3-2-1, a second for each digit
tail_s = 1.5
film_gain_db = -12.0                        # film audio level in the headphones while recording
voice_gain_db = 0.0                         # level of takes played back with P and Shift+P (0 at most); export ignores it
passage_gap_s = 1.0                         # lines closer than this form one passage (see "Passages")

[check]
whisper_model = "ggml-large-v3-turbo.bin"   # resolved in the models directory
language = "en"
```

`script.toml`:

```toml
[[line]]
id = "hook"                 # stable slug [a-z0-9-], unique; takes and ledger refer to it
start = 0.0                 # seconds of film time where the line should begin
end = 5.0                   # end of the slot; optional, defaults to the next line's start or the film's end
text = "I put our whole family tree together. Everyone looked at it once, and never came back."
note = "warm, a little wry"  # optional direction for the narrator
```

Validation (`status` reports, the app refuses to record until fixed): ids unique and slug-safe, starts in increasing order, `end > start`, everything within the film's duration. Changing a line's `id` orphans its takes, which `status` reports.

### Writing files safely

The app, the CLI and agents editing by hand may all touch the folder.

- **One lock.** Every Takewise writer takes an exclusive advisory lock on `.lock` (`flock`) for the duration of a write: a script edit, a take allocation, a ledger append. Writes are short; the lock is never held while recording.
- **`script.toml` edits** are format-preserving (`toml_edit`): re-read the file under the lock, change one field of one line by id, write a temp file, rename over. The app watches the file and reloads; an edit made in the app against a version that changed on disk is rejected with a message instead of overwriting it. Agents may edit the file directly while the app is closed. Only `takewise script set` (below) is protected against concurrent edits; a direct edit while the app is open can be overwritten.
- **Takes.** Recording streams to `takes/<line>/.<uuid>.wav.partial` from a writer thread fed directly by the capture, with its metadata (everything the `recorded` event needs) already in `takes/<line>/.<uuid>.json.partial` when the film is scheduled. The writer holds an exclusive advisory lock (`flock`) on the partial WAV while recording and rewrites the WAV header and syncs at least once per second, so the file is a valid WAV up to the last flush. Every captured sample is also kept in memory until the take is committed: when the metadata or the WAV cannot be written, the window shows the error, keeps recording, and writes the take from memory on stop (retrying until it succeeds). On stop, the WAV is finalized and fsynced, the metadata rewritten with the line's position at that moment, then under the lock the next free number is allocated, the metadata renamed to `NNN.json`, the WAV to `NNN.wav`, and the `recorded` event appended; the WAV stays locked until then. When finishing the WAV fails, or the take could not be begun on disk, the take is written again from memory, never over the audio that is there: into a new file beside the partial WAV, which is locked before it holds anything, fsynced, and renamed over the partial WAV only when it is whole. A failure on the way leaves what the recording had streamed as it was, so a crash after it still has that much to adopt. The partial WAV stays locked throughout (the lock kept from the recording, and the new file's from before the rename; both are held until the commit succeeds or the window exits), so a repair never adopts a take the window still owns. A passage's audio is saved from memory the same way. File locks are released explicitly when their holder is done, not by closing the file: a process being started meanwhile (`ffmpeg` for a check) briefly shares the open file and would otherwise keep the lock a moment longer. Take numbers are allocated only under the lock. While a take or passage exists only in memory (saving failed, and its audio and metadata are not complete on disk for a repair to adopt), the window refuses to close and ⌘Q refuses to quit: the window says how many are unsaved and why, keeps retrying every two seconds, and closes when asked again once they are saved. Nothing is ever discarded to let it close; what cannot be saved gets a rescue copy first (see "Rescue copies" below).
- **Passages** (see "Passages") stream into `takes/.passages/.<uuid>.wav.partial` with the same writer, lock and flushes as a take, beside the sidecar `.<uuid>.json.partial`. On stop the cuts are written into the sidecar, then the sidecar is renamed to `<uuid>.json` and the audio to `<uuid>.wav`; the renames are the commit point, and nothing changes a published passage. Its takes are then written one piece at a time, each committed like any take (numbered and logged under the lock). A piece's partial files are named after the passage and the piece (`.<uuid>-<index>.wav.partial`), and whoever holds the lock on that audio writes the piece, so the window and a repair never write one twice; the audio is written whole before its metadata exists, so a crash leaves nothing a repair could adopt half written.
- **Ledger appends** are one `write` of one complete line with `O_APPEND`, under the lock; when the file does not end in a newline (a torn last line from a crash), the writer first appends one, so the new event starts on its own line. Readers skip any line that does not parse and `status` reports it as a notice. Several events that belong together (the choices of `choose --passage`) are not appended in one `write`, which could tear between two of them and leave a reader with the first few: under the lock, a copy of the ledger with every byte it has, followed by the events, is written to a temp file, fsynced and renamed over `takes.jsonl`, and the directory is fsynced. Nothing in the ledger is changed or removed by that either: the event history stays append-only, though the file is a new one afterwards. A reader that keeps `takes.jsonl` open across a batch still holds the old file, so live readers reopen the path (Takewise reads the ledger whole each time, and the window watches the folder, not an open file).
- **Recovery.** A `NNN.wav` without a `recorded` event (crash between rename and append) is adopted from its `NNN.json` with a `recorded` event marked `recovered: true` the next time the app or `takewise status --repair` runs; without its `NNN.json` it is only reported. The metadata names its partial WAV, so a `NNN.json` whose WAV is still `.<uuid>.wav.partial` (crash between the two renames) is completed the same way; a `NNN.json` with no audio at all is only reported. A `.<uuid>.json.partial` whose `.<uuid>.wav.partial` holds audio and is not locked (a crash mid-take) is adopted the same way: the WAV's lengths are fixed from its size on disk, it is numbered, and its `recorded` event is marked `recovered: true`; a locked partial belongs to a live recording and is never touched. Any other leftover `.partial` is reported and kept, never deleted. Directories under `takes/` whose name starts with a dot (`.passages`, `.room`) hold no takes and are never searched for them. A passage partial that is not locked (a crash mid-take) is finished the same way: its lengths are fixed from its size on disk and, when its sidecar has the film time of its first sample, its cuts are computed and it is published (marked `recovered`, as its takes are) and cut into takes; without that film time nothing says where to cut it, so it is kept and reported with its path (`passage-unplaced`). A publish interrupted between its two renames is completed, and every published passage that lacks takes is cut into them; a passage that cannot be finished or cut (its audio no longer matches its sidecar, say) is reported with the reason and does not keep the rest from being repaired. Cutting skips a piece whose passage id and index already have a `recorded` event, which is also how a piece adopted after a crash between renaming its `NNN.wav` and appending its event is recognized.
- **Rescue copies.** Added 2026-11-24 after a review found that a quit from outside could discard audio held only in memory. The window can refuse to close and can refuse ⌘Q, but not a quit that macOS starts (the Dock's Quit, a logout, a shutdown): GPUI's macOS platform implements only `applicationWillTerminate`, which runs once termination is underway, and exposes no `applicationShouldTerminate` or other hook that could cancel it (checked in gpui-pre 0.3.12, which gpui-kit 0.10.0 pins; its `on_quit` callback returns a `bool` that the macOS platform ignores). So nothing may depend on the refusal. When the window goes while a take or passage is still only in memory, after one more attempt to save it, it writes that audio to `rescue/<project folder name>-<timestamp>/` beside the settings file (`~/Library/Application Support/Takewise/rescue/`; `takewise_core::rescue`), which does not depend on the project's disk: each take or passage as a WAV like a take's, written and fsynced under a temp name and renamed, then a JSON file of the same name (`kind`, `project`, `rescued_at`, `audio`, `sample_rate`, `samples`, `lines`, `restore`, `sidecar`), and the folder and its parents are fsynced. A copy's name (`NNN-take-<line>`, `NNN-passage`) is reserved before anything is written, by creating its WAV empty and only if nothing has that name, and the audio is renamed over that empty file alone, so no copy ever replaces a file in the folder; a line id longer than 80 bytes, and a project folder name longer than 200, is cut to its beginning and eight hex digits of its SHA-256 to keep the name within what a folder allows, and the JSON file has both whole. When the audio is written and its JSON file cannot be, the WAV stays and the folder is fsynced all the same: the window says where the audio is, and still counts it as having no rescue copy. `sidecar` is exactly what the project stores beside the partial audio (the line's snapshot, the device, the offset from the line's start; for a passage its lines, latency and first sample's film time), and `restore` names the two partial files to create in the project, so bringing a copy back is the recovery that already exists: put the files there and `status --repair` adopts them. That is done by hand for now (`docs/reference.md`, "Rescued audio"); nothing writes into a project from the rescue folder, and nothing removes a copy. The same copy is the way out when the project's disk is gone for good: the first request to close is refused and names the folder, the second writes the copy and, once it is synced, closes. A copy that cannot be written either leaves the window open with the audio in memory; on a quit from outside there is then nothing left to try, and the window says on stderr what was lost, or where the audio is when only its JSON file is missing. Audio with a rescue copy no longer holds the window, saving it into the project is still retried while the window lives, and a take saved after all says its copy is spare. `status` lists each rescue folder that holds audio of the project (`rescued-audio`), with the WAVs in it that have no JSON file (in a folder without any JSON file, which only its name ties to a project, for every project of that folder name), and says to delete the folder only once every recording in it is back; a window opened on the project says the same.

### The ledger

`takes.jsonl` is an append-only history of events: no event is ever changed or removed, and every earlier byte is kept. A single event is appended in place; a batch (`choose --passage`) replaces the file with a copy that ends in the batch (see "Ledger appends" above), so follow it by reopening the path, not by holding it open. Each line is one event: `{"v": 1, "at": RFC 3339, "kind": …, "line": id, "take": n, …}`.

- `recorded`: `file`, `sample_rate`, `samples`, `device`, `channel`, `line_offset_s` (film time of the take's first sample minus the line's start when the take is stopped and committed; negative because capture begins with pre-roll), a `snapshot` of the line (`text` as it was when the take started, the text read; `start` and `end` at that moment), so a line moved with **M** during the take keeps the take at the film time it was recorded at, and a text edited during the take shows the take as recorded against old text, and optionally `dropouts`: how many gaps the capture had (buffers arriving later than the previous one ended, by more than 1 ms), each filled with silence so later audio keeps its timing. Takes recorded before it existed, and takes recovered after a crash, have no `dropouts`; readers treat it as unknown. Optionally `film_shift_ms`: the take's audio is contiguous and placed by its first sample, so when the film stalled or changed rate after the take started, the largest distance between where the film really was and where the take places it (until the film's end), recorded only when above 5 ms; the window then shows "film stalled during the take; placement may be off by N ms". Absent on takes without a shift and on takes recorded before it existed; readers ignore it when absent. Optionally `passage`, on a take cut from a passage: `id` (the passage's uuid; its audio is `takes/.passages/<id>.wav`), `index` and `count` (which piece of how many), `from_sample` and `to_sample` (the piece's range in the passage file; one piece's `to_sample` is the next one's `from_sample`) and `preroll_floor_dbfs` (the noise floor of the passage's pre-roll, which stands in for the pre-roll a piece does not have). A reader from before passages ignores it and sees an ordinary take.
- `checked`: `snapshot` checked against (text and slot), transcript with word times, word differences, `speech` (start and end in source seconds, from the energy detector), `speech_onset_s` (where the words start as the early-start rule measures it, after a breath set apart from them; absent without speech and on older checks), `overrun_s`, `peak_dbfs`, `clipped_samples`, `noise_floor_dbfs`, `verdict` (`keep`, `retake`, `listen`), `reasons` (list of `{code, message}`), `checker` (whisper model and Takewise version).
- `judged`: an outside judgment: `snapshot` judged against, `by` (free text, for example `claude-opus-5-5`), `verdict`, optional `score` 0–1, `reason`.
- `chosen`: `by` (`narrator` or the agent's name).

Snapshots store the resolved slot end, so moving a neighbour also changes them. Folding: a take's effective verdict is its latest `judged` event whose snapshot matches the current line (text exactly, start and end within 1 µs), otherwise its latest matching `checked` event, otherwise none (`unchecked`). A judgment or check against old text or an old slot is shown as stale; checks are re-run, judgments are not. A line's choice is its latest `chosen` event of a recorded take; a choice of a take without a parseable `recorded` event is ignored and reported as a `choice-without-take` notice, so the line counts as unchosen. No other event kinds in v1. A change of film (`takewise film`) is not a ledger event: every event belongs to a line and a take, and a reader from before it would count an event of a new kind as a bad line and report it forever; the change is recorded as `[previous_film]` in `project.toml`, which older versions ignore and keep.

## Timing model

Takes belong to their line, not to absolute film time. A take's position is `line.start + line_offset_s`, so when the narrator presses **M** or an agent moves a line's `start`, its takes move with it; overrun checks are re-run against the new slot.

Capture starts at the beginning of pre-roll (so the noise floor before speech is recorded) and stops at Space or `tail_s` after the slot's end; when the film ends first (the last line's slot runs to the film's end), it stops `tail_s` of host time after the film reached its end. Space starts capture first; once its first buffer arrives, the film is scheduled to start at least 300 ms ahead (the players need the lead), so a slow input never eats into the pre-roll. From the scheduled start on, the window reads the player's timebase back every frame and records each departure from the mapping in effect (a late start, a stall, a rate change) in the take's timebase history, which places the samples: the first read-back replaces the scheduled mapping for the whole take, count-in included, so a late start moves the take, and the take's first sample is placed with it when the take is committed; the prompter and the automatic stop follow the film as it really plays. The loopback calibration (`takewise calibrate`) runs this same start routine, so it measures the window's path. When a line starts less than `preroll_s` into the film, the film holds its first frame during the count-in and starts playing at film time zero; the capture's first samples then have negative film time and are cropped at export.

The clock mapping is the spike's job to prove. The model: capture buffers carry host timestamps; the player's timebase maps host time to film time. The film time a sample belongs to is the film time *heard by the narrator* when the sound was made, so the mapping must account for both input latency (mic to timestamp) and output latency (player to headphones). The spike establishes which of these the capture timestamp and the player clock already include, so neither is subtracted twice. `latency_offset_ms` is a manual correction set from a loopback test: a film with beeps at known times played through headphones held to the mic; the recorded beeps must land at their film times within ±20 ms, including at film time zero and after repeated seeks. A clap test is not sufficient. Bluetooth headphones are discouraged for recording: their delay can change after reconnecting, so the latency must be measured again then (L in the window); `doctor` warns when the output device is Bluetooth.

## The recording screen

```text
+--------------------------------------------------+----------------+
|                                                  | 1 hook     ✓ 3 |
|                  film (16:9)                     | 2 today    ! 2 |
|                                                  | 3 question  –  |
+--------------------------------------------------+ 4 quiz      –  |
|  0:05.2  ▓▓▓▓▓▓▓▓▓▓░░░░░░░  slot 3.0 s   ▮▮▮░ mic | ...            |
|                                                  |                |
|  So I built Kindred around a page worth          | takes of 2:    |
|  opening again.                                  |  1 retake: 'a' |
|                                                  |    missing     |
|  next: One question a week, and every answer…    |  2 keep  ☆     |
+--------------------------------------------------+----------------+
 Space record/stop · Enter choose · R retake · P play in context · M mark start · E edit
 ⇧ + Space/Enter/P: the whole passage
```

- The current line is large; the next line is dimmed below it. A bar shows the slot running out, and the words fill from left to right at an even pace across the slot (karaoke-style pace guide, by character count; Niklas's original idea, kept because it is small). A level meter shows the input.
- **Record (Space):** the film starts `preroll_s` (3 s by default, a second for each digit) before the line's start; a 3-2-1 count-in shows on screen over the pre-roll's last three seconds, each digit the whole seconds left before the line, on a dark plate so it reads over a light film as well; recording runs until Space again or `tail_s` after the slot ends. Film audio plays at `film_gain_db` in the headphones; the mic is monitored only when the narrator has turned monitoring on.
- **After the take:** the verdict shows next to the take as soon as the checks finish, until then "checking…", with the reason that explains it below. Checks run one at a time on a worker thread, after every commit and whenever a reload finds takes without a check against their line as it is now (an edited text or a moved slot). When whisper-cli cannot be set up, takes still get their sound and timing checks, with `listen` and the reason. The top-ranked take gets a hollow star (proposed) once its check is in and only when its verdict is `keep` or `listen`: a proposed `retake`, or a take still being checked, has none, while `status --json` still names it as `proposed`. A chosen take gets a filled star, whatever its verdict.
- **Enter** chooses the selected take, **R** records another, **P** plays the line in context (pre-roll, take, tail) with the selected take locked to the film, **↑/↓** move between lines and **←/→** between takes. The line list scrolls just enough to keep the current line in view whenever it changes.
- **With Shift, the same keys work on the passage** (see "Passages"): **Shift+Space** records from the current line through the end of its passage, **Shift+P** plays the selected take's passage from that take's line to its end, **Shift+Enter** chooses it for every line it has a take of. The line list shows each passage of several lines with a thin bar beside them, and a take cut from a passage says which piece it is ("passage 2/3"). During a passage take the line just read stays dimmed on a row above the current line for 1.5 s after the prompter moved on.
- **M** sets the current line's start to the playhead while the film plays, clamped between the previous line's start and the line's own slot end. **E** edits the line's text in place; the draft belongs to the line and the `script.toml` version it was begun on, so a script changed meanwhile refuses it, and a line removed meanwhile is never replaced by another. Both write `script.toml` as described above.
- **C** opens the setup check and **L** only its latency step, to measure the latency again whenever it may have changed (see "Setup check").
- **Closing** the window or quitting keeps a take in progress. While a take or passage exists only in memory because saving it failed, neither happens: the window says why and keeps retrying, and asked a second time it writes a rescue copy outside the project and closes (see "Writing files safely").
- When the input device is missing or not running at 48 kHz, the screen says so, names the available devices, and does not record. On the RØDECaster Duo the mic appears in the two-channel devices "Main Stereo" and "Chat"; which channel carries the mic depends on RØDE Central's routing, so the level meter is how the narrator confirms the choice.

### The start window

Opening `Takewise.app` without a project (from the Dock or Finder) shows the start window: **Open project…** (⌘O, also in the File menu), the projects opened recently (kept in `recent.json` beside `settings.toml`, resolved and each once; folders that are no longer projects are left out) and **Install Command Line Tool…**. A folder with a `project.toml` opens. Any other folder asks for the finished film and starts a project as `takewise init` would: in the folder itself when it is empty or named `….takewise`, else in a new `<film name>.takewise` inside it; when that `<film name>.takewise` is already the project of this film, it opens instead of failing; when it is the project of another film of the same name (`Promo.mp4` beside `Promo.mov`), the new project is `<film file name>.takewise` (`Promo.mov.takewise`) and the window says so. A project whose recording window is already open is brought to the front rather than opened a second time. `takewise record <dir>` skips the start window and opens the recording window directly.

The menu bar follows the Mac's conventions and is the same in every window: **Takewise** (About, Install Command Line Tool…, Services, Hide, Hide Others, Show All, Quit), **File** (Open Project…), **Window** (Minimize, Zoom, Close Window) and **Help** (the README, its keys, the running version's release notes, a new issue, all on GitHub). About is the standard AppKit panel, so it shows the bundle's icon, version, build and copyright like any Mac app's, with a line on what Takewise is and the repository's link as its credits.

## Checks

All local, run after each take and by `takewise check`. Recording and choosing work without them; a failed check never blocks the narrator.

- **Speech and timing (primary, milestone 1 because export needs it):** an energy detector on the take finds speech start and end relative to the noise floor measured in the pre-roll. Overrun is speech end past the slot end; early start is speech start before the line's start.
- **Words:** transcribe with whisper.cpp (`whisper-cli`, Homebrew `whisper-cpp`) *without* the script as a prompt, so the model does not hear what it expects. Normalize case, punctuation and contractions, and turn numbers into values on both sides ("1,500", "fifteen hundred" and "one thousand five hundred" are all 1500; years said in two parts, decades, ordinals, decimals and currency likewise; a decimal compares by value, so "3.50%" is "three point five percent"; "three dollars and fifty cents" is $3.50; cents not named stay a number of their own, so "five dollars twenty years ago" matches "$5 20 years ago" and "seven pounds eight ounces" "7 pounds 8 ounces", while the alignment still matches "three dollars fifty" against "$3.50"; a sign is kept, so "-5", "minus five" and "negative five" are −5, never 5, and "-$5" is "minus five dollars", never "$5"; between two numbers, "minus" and a free-standing dash are the word minus, so "ten minus five" matches "10 - 5"). A number never runs across punctuation ("pick twenty, one at a time" is 20 and one, not 21), and "first" and "second" are ordinals only when attached ("twenty-first"), never in "a sixty second timer"; a number split in two on one side still matches its joined form on the other ("sixty second" and "62nd", "60-second" and "sixty-second"), a clock time with a colon on either side matches "eleven thirty", "11 30" or whisper's "11.30" on the other, a full hour such as "10:00" matches "ten", "10", "10.00" or "ten o'clock" (without a colon, two numbers are never a time), and "alright" matches "all right". "Three fifty" for $3.50 stays a possible mishearing to listen to, since it may be 350. Then set aside the annotations whisper writes for sounds (`[BLANK_AUDIO]`, `(coughs)`, `[Music]`, `[background music playing]` over several words), then align the words with the line text and report missing, extra and substituted words with times, named as written in the script or said in the transcript ("second", not "2nd"). Two words on one side against their concatenation on the other ("every day" and "everyday", "every one" and "everyone") are one substitution, so a possible mishearing to listen to, since they often mean different things; two words joined by a hyphen are one word spelled two ways and match ("voice-over" and "voiceover", "e-mail" and "email"). A script word with an apostrophe accepts what it sounds like ("link's" a heard "links" or "link is", "family's" "families", "Niklas's" "Niklas"); a plain script word does not, so "the light is below" heard as "the lights below" is a difference. The exact output format of the installed `whisper-cli` is verified before relying on it.
- **Sound:** peak dBFS, clipped samples (at or above −0.1 dBFS), noise floor.
- **Verdict, first matching rule wins:**
  1. No speech detected → `retake` ("no speech").
  2. Clipping → `retake`.
  3. One or more missing or extra words → `retake`, naming them.
  4. Overrun beyond 0.25 s or early start beyond 0.3 s → `retake`, with the amount. Early start is measured from the energy speech start, unless at least 120 ms of silence lies between it and the first transcribed word: then the sound before is a breath or a noise before the words (seen on the real Kindred take, line 4: a breath 0.52 s early), and the speech starts where the sound resumes after the last such gap, not at the first word's DTW time, which lands late. Without such a gap the energy start is the first word's onset, however late DTW places the word (0.08 to 0.20 s after the real onset on the Kindred lines). A take cut from a passage is held to this rule only at the passage's edges, and has two `listen` findings of its own (see "Passages").
  5. Transcription failed or unavailable → `listen` ("words not checked"). This includes a tool that does not finish in time (`ffmpeg` 30 s, `whisper-cli` 120 s), which is stopped, and output with word times missing, out of order or out of range. Such a check does not count as current: `takewise check` and the window's queue run it again. When the only takes left are ones whose transcription cannot be set up (the tool or model is still missing), `takewise check` says why and exits 2 instead of reporting nothing to check.
  6. Only substitutions (likely mishearings of names or numbers) → `listen`, naming them.
  7. A sound whisper annotates inside the speech, such as `(coughs)` or `[Music]` → `listen` (`non-speech-sound`), naming it; an annotation outside the speech (`[BLANK_AUDIO]` in the pre-roll) is dropped.
  8. Speech less than 30 dB above the take's own pre-roll floor → `listen` (`background-noise`, "background noise only 24 dB below your voice"); skipped when the pre-roll is digital silence (a gated interface). See "Noise per take".
  9. Otherwise → `keep`.
  Thresholds are tuned on real takes (the Kindred narration recorded on 2026-11-22), not only on synthetic `say` fixtures.
- **Re-checks:** when only a line's slot moved since a take's check (the same text), checking it again recomputes the verdict from that check's words and a fresh energy analysis, without running whisper; the sound finding of rule 7 carries over. The `checked` event's `checker` names the whisper model and how the audio is prepared before transcription (`pre=hp60+norm` since milestone 4b; checks without the tag were made with `pre=none`); a check by another model or preprocessing is transcribed again, as is a take whose current check is re-run explicitly. Such a check is not current: `check` (and its `--stale-only`) and the window's list of takes to check pick it up as stale while transcription can be set up, so changing `[check] whisper_model` re-checks the takes without turning their words into failures while the new model is missing.
- **Ranking** among a line's takes, using effective verdicts: takes whose file is missing rank last and are never proposed; then `keep` before `listen` and `unchecked` (equal) before `retake`; then fewer word differences; then smaller overrun; then outside `score`; then newest. The top take is proposed, never chosen automatically.

One binary, `takewise`. Every command takes the project directory and supports `--json`. Exit codes: 0 success, 1 a finding (for example `export` refusing, or `status --strict` with problems), 2 usage or setup errors.

## Export and Resolve handoff

The narration file (`narration.wav` or `narration.flac`) is mono, starting at film time zero and exactly as long as the film. A 24-bit WAV tags its one channel front centre, so ffmpeg and editors read it as plain mono rather than a left channel alone; takes and room tone are tagged the same way from 0.1.1 on. `[export]` sets its format, sample rate and bit depth for both processing profiles; a project without `[export]` gets 48 kHz 24-bit WAV with `raw` processing. Export removes a narration file of the other format, so only one narration file sits beside the manifest.

For each line, the chosen take is used; a line without one makes `export` fail with the line ids, unless `--use-proposed` uses the proposed take (the manifest records `by: "proposed"`), which it refuses with `no-acceptable-take` when that take's effective verdict is `retake`; a line with no takes at all always fails. A used take in which no speech is detected also fails export, naming the line, unless it is a piece of a seam run that has speech elsewhere (below). A used take recorded against different text than the line has now is exported, with a `recorded-against-old-text` warning in the manifest (and a notice in `status`). From the take, the source range is its speech, extended by 150 ms on either side and clipped to the take. The speech starts where the early-start rule measures it: with the take's latest check against the line as it is now, a breath or noise set apart from the first word by a gap of at least 0.12 s is not its start, so a breath over the end of the previous line is no overlap. A source sample `i` lands at destination sample `round((line.start + line_offset_s) × 48000) + i`; trimming never shifts the speech. Ranges are cropped to `[0, film length)`; a take whose speech (without the margin) lies entirely outside that range fails export with `speech-outside-film`, and one whose speech lies partly outside is exported with a `speech-cropped` warning in the manifest that gives the unclamped speech times (the line's `speech_film_s` is clamped to the film). When the speech (without the margins) of two used takes overlaps, export fails with `overlap` and names both lines, so the narrator can choose another take or move a start; `status` shows the same for chosen takes beforehand as a `speech-overlap` notice (from the speech each chosen take's latest check stored, starting at its `speech_onset_s` as export does, so both name the same pairs; a check from before the onset was stored falls back to its energy speech start, which still includes such a breath). When only their margins overlap, the gap between the two speeches is split at its midpoint, and each take keeps its margin up to there. Each placed range gets 10 ms fades, shortened where a split margin leaves less room, so a fade never cuts into the speech; when two speeches are less than 20 ms apart, the manifest gets a `tight-gap` warning naming both lines.

A passage stays continuous. Before trimming, consecutive lines are joined into a seam run when their used takes are pieces *i*, *i+1*, … of one passage, each piece ends in the passage file where the next begins (its `to_sample` is the next one's `from_sample`), and each take still lies where it was recorded: its own placement is within one sample of its place in the run, which the run's first take sets. The seam runs are established first, before any take is asked for its speech or trimmed. A seam run is exported as the passage was recorded: one stretch of audio, the pieces' files one after the other (sample for sample that range of the passage file), placed where its first take lies. The rules above apply to its outer edges only: it starts 150 ms before the first speech in it (by that take's check) and ends 150 ms after the last, its margins are split against its neighbours', and it fades in and out once. Speech is required of the run, not of each piece: a narrator who reads a line early or late leaves that line's own piece with only the room, its words in the piece beside it. Such a piece stays where it is in the run and gives a `passage-piece-without-speech` warning that names its line (its `speech_film_s` is an empty range, where the speech after it begins or the speech before it ends). At an outer edge of the run, the passage's piece on that side is not part of the run; when the export does not use that piece's take at all (its line was read again on its own), words read into it are in no exported audio, so the warning then says the line may be missing from the export and names that take's file. It stays a warning: the line may as well have been read into the piece on the other side, which is exported. Such a piece is trimmed away whole, and its `source_samples` and `dest_samples` are empty ranges, at its take's end and the run's start when it lies before the run, at its take's first sample and the run's end when it lies after; every line's ranges lie within its take file and the narration. A run without any speech, and a piece without speech that stands alone, still fail with `no-speech`. Between its lines there is no cut and no fade, so the breaths and the room between the sentences stay as they were read. A line moved since it was recorded, or one whose used take is not the next piece (a line read again on its own), is not joined: the cuts beside it are made as between any two takes, and the lines on either side stay joined to their other neighbours. Speech of another take that falls into a pause a seam run keeps refuses with `overlap` too, naming that take's line and the line before the pause (`status` does not announce this case beforehand).

Export first compares the film on disk with `[film_info]` (size, modification time and, when `ffprobe` can read it, duration) and refuses a missing or changed film (`film-missing`, `film-changed`): the timings were made against the measured cut, so `takewise film` must accept the new one first (`--film <path>` for a render at another path). It reads the project, script and ledger under the project lock, releases the lock while it loads and analyzes the takes, cleans them and renders the narration to a temp name (`ffmpeg` can take a while, and the window must stay able to record and choose), then takes the lock again and publishes only when `project.toml`, `script.toml` and `takes.jsonl` are byte for byte what it read and the film still probes as it did when the export started (size, modification time, duration); a film that went missing or changed meanwhile refuses with `film-missing` or `film-changed`. Each probe runs `ffprobe` at lower priority with a 10 s timeout, so a stalled probe never holds the lock; one that stalls is stopped and refuses with `film-probe-timeout`. When they changed, it renders once more from the new state, then refuses with `state-changed`. Publishing writes the manifest to a temp name, removes the old manifest, renames the narration into place, and renames the manifest last, so an interrupted export never leaves an old manifest beside a new narration. A refused export writes nothing and removes an existing `manifest.json`, so no stale pair looks valid (the export is regenerable; takes are never touched).

`manifest.json` lists the film (path, duration, size, modified), the WAV it describes (`narration`: file, size, SHA-256) and per line: id, text, take file, `by` of the choice, source sample range, destination sample range, speech start and end in film seconds, and `words_film_s`: the transcribed words (`{text, start, end}`, film seconds) from the take's latest check against the line as it is now, omitted when there is none. A line joined to the next in a seam run has `seam_with`, the next line's id: its source range runs to the end of its take, the next line's starts at 0, and its destination range ends where the next line's begins. Every line keeps its own ranges, speech and words.

For Resolve, an agent imports the narration file onto a new audio track at the timeline start, or places the individual takes (always the raw originals) at the manifest's positions, and adds a marker per line. The README documents this recipe; Takewise itself has no Resolve code. The milestone that adds export verifies the narration file against the loopback beeps and imports it into Resolve once.

## Architecture

A Cargo workspace:

- `takewise-core`: the project format, lock and write protocol, ledger and folding, script edits, audio analysis, word alignment, verdict rules, ranking and export. No GUI, no unsafe code, fully tested.
- `takewise-media`: the macOS bridges, the only crate allowed `unsafe` (each block with a `SAFETY` comment): film playback with AVPlayer, video frames for GPUI, take playback locked to the film, audio capture from a chosen device and channel, and the clock mapping.
- `takewise`: the binary, CLI subcommands and the GPUI recording window.

The media path below was proven by the milestone 0 spike on 2026-11-22 (decision "Play, capture and align media through AVPlayer, GPUI surfaces and cpal").

**Playback.** AVPlayer plays the film. `AVPlayerItemVideoOutput` delivers NV12 full-range `CVPixelBuffer`s (Metal-compatible, IOSurface-backed), polled once per frame and drawn with GPUI's `surface()` element; text draws on top of it. A second AVPlayer started at the same host time plays a take locked to the film (within 0.01 ms in the spike).

**Capture.** cpal opens an input stream on the named device and takes one channel; optional monitoring taps this stream (see "Setup and sound") and never opens a second capture. Each buffer's film time is `timebase(callback_host_time + i / sample_rate − L_in) + latency_offset_ms`, where `L_in` is the device's input latency plus safety offset plus stream latency from CoreAudio (`objc2-core-audio`). cpal's own capture timestamp is not used, because it leaves out the stream latency. AVPlayer's clock already accounts for output latency, so it is not subtracted. Changes of the player timebase (seeks, rate changes) are kept as a history, so a buffer is mapped with the timebase that was valid when it was captured. For a start scheduled at a later host time, the player's own timebase stays stopped until that moment, so the history takes the scheduled mapping (film time at the start host time, rate 1) from the call on; once playing, the player's timebase matches it within 0.02 ms. Before the first take after opening, the film plays briefly muted, so a cold output device does not shift the first take.

**Calibration.** One loopback measures only the total of input and output latency, so `latency_offset_ms` is calibrated per device pair with the loopback test. In the spike, beeps landed 31.5 ms late (standard deviation 0.01 ms) on the MacBook's speakers and mic, at film time 0.1 s and after seeks; CoreAudio's reported latencies alone left −19.5 ms, a calibrated offset under 1 ms. `takewise calibrate --write` stores the offset only when every detected beep landed within 20 ms of the mean error; otherwise it refuses (exit 1, `inconsistent-beeps`) and leaves `latency_offset_ms` as it is. The offset applies only on the route it was measured on (`effective_latency_offset` in the core): with another input, output or capture buffer than `[calibration]` records, takes are placed without it and `calibration-stale` asks for a new loopback test, since an offset from other devices would shift every take by the wrong amount.

**Microphone permission.** A bare binary inherits the permission of the app that launched it, and capture hangs while that app's prompt is unanswered. `takewise record` therefore launches a signed `Takewise.app` (with `NSMicrophoneUsageDescription`) so the permission belongs to Takewise; release builds are Developer ID signed, since ad hoc permission grants reset on every rebuild. The other CLI commands stay a plain binary.

**Transcription.** Shell out to `whisper-cli` with JSON output and word timestamps rather than linking whisper.cpp, so builds stay simple. `takewise doctor` reports a missing binary or model.

## Setup and sound

Added 2026-11-23 at Niklas's request and revised after council review (Claude Fable 5.2: 6/10, GPT Sol 6.2: 7/10). The aim is outcomes good enough to use without post-production, while staying easy: the app guides the narrator to a good setup instead of expecting audio knowledge.

### Settings schema

New tables in `project.toml`; a project without them behaves as before (no monitoring, `raw` export):

```toml
[output]
device = "RODECaster Duo Main Stereo"   # where film audio and monitoring play

[monitor]
enabled = false
volume_db = -6.0

[calibration]                            # which device pair `input.latency_offset_ms` was measured on
input = "RODECaster Duo Main Stereo"
output = "RODECaster Duo Main Stereo"
buffer_frames = 512                      # the capture buffer during the measurement
date = "2026-11-23"
# from = "remembered"                    # copied from an earlier measurement (milestone 6)

[export]
format = "wav"        # wav or flac
bit_depth = 24        # 16 or 24
sample_rate = 48000   # 48000 or 44100
processing = "clean"  # raw or clean; new projects default to clean

[setup]               # written by the setup check
date = "2026-11-23"
input = "RODECaster Duo Main Stereo"
channel = 1
output = "RODECaster Duo Main Stereo"
room_floor_dbfs = -68.0
speech_to_noise_db = 46.0
# from = "remembered" # adopted from another project's check today (milestone 6)
```

`[calibration]` also records the capture buffer size; when the input, the output or the buffer size differs from it, or a project has an offset but no `[calibration]` (measured before this section), `status` and the window warn that the latency calibration is stale. `status` likewise warns when the devices differ from `[setup]` or no setup check has run. The last device choices are also saved as defaults for new projects in `~/Library/Application Support/Takewise/settings.toml` (`TAKEWISE_SETTINGS` names another file); `init` starts a project with them. Device and route changes take effect between takes, never during one. Latency measurements and setup checks are remembered across projects beside that file (see "Remembered setup" below).

### Recording screen additions (milestone 4a)

**Audio panel** (toggled with **A**, usable while the film plays): input device, input channel and output device as pickers. Every channel of the selected input shows its own live meter, so the channel that carries the mic is obvious. A missing device is explained in plain words ("RODECaster Duo is not connected. Connect it or pick another input."). An input not at 48 kHz offers a "Switch to 48 kHz" button (sets the device's nominal rate through CoreAudio). The output is where the film plays, and the takes and passages played back with P and Shift+P too: a take heard through another device than the film would be no check at all. A chosen output that is not connected is never replaced by the system output: P, Shift+P and recording refuse and say so until it is connected or another is chosen, and the window moves to it as soon as it appears.

**Levels** (always on screen, under the takes list): **Film** (`[record] film_gain_db`) and **Voice** (`[record] voice_gain_db`, the level takes and passages play back at; 0 dB by default and at most, since AVPlayer cannot amplify; export never uses it), and **Monitor** (`[monitor] volume_db`) once monitoring can run. Each is a slider with its value in dB, and the film and monitor also have keys that match the typed character, so they work on QWERTY and QWERTZ alike: `-` and `+` for the film, `,` and `.` for the monitor; a key moves its slider. They can change during a take and during a playback, and apply at once; `project.toml` is written once a change has rested for half a second, between takes. They sit beside the takes rather than in the audio panel because they are what changes while listening, take after take, while the panel's devices are set once.

**Monitoring** (**H**, also a visible toggle in the panel). Off by default. **H** works between takes only, since starting an output stream mid-take risks a dropout. A saved `enabled = true` resumes monitoring on open only when the devices are the ones it was enabled on, with the toggle visibly on; otherwise it starts off. When on, the existing capture callback also writes into a ring buffer that an output stream plays at `monitor.volume_db`; monitoring never opens a second capture and never changes the buffer size of the capture stream, which is fixed per session (128 frames, for every take whether monitored or not) so calibration stays valid. In v1 monitoring requires the input and output to be the same device (a shared clock, such as the RØDECaster's mic and headphone outputs); with different devices the toggle explains why it is unavailable. The panel shows the estimated mic-to-ear delay (input latency + buffer + output latency, labeled as an estimate) and warns above 15 ms, which rules out the built-in mic (about 50 ms). Monitoring is refused while the output is the built-in speakers (feedback). Because CoreAudio cannot tell whether an interface monitors in hardware, the panel always shows a hint: "If your interface has direct monitoring, use it instead and leave this off, or you will hear yourself twice." A monitoring failure mutes only the monitor; recording continues.

**Monitoring spike, the gate for 4a.** On the RØDECaster with wired headphones, with AVPlayer running: zero dropouts over five minutes of capture at 128 frames; loopback placement within ±20 ms and unchanged (within 2 ms) between the device's default buffer and 128 frames, and between monitoring off and on; the measured mic-to-ear delay. If the device refuses 128 frames or any criterion fails, capture keeps the device's default buffer and 4a ships the panel, meters and scrolling with only the direct-monitoring hint, without software monitoring.

**Meters.** The input meter shows peak with a 1.5 s hold and a shaded target band from −18 to −6 dBFS. A "near clipping" light turns red at −1 dBFS and stays red until **K** or the next take; a take whose samples reached −0.1 dBFS is marked "clipped" in its row (the verdict rule's threshold).

**Long lines.** Up to three lines of text show at full size. A longer line scrolls smoothly so that the words under the pace fill stay on the middle row; the first and last rows hold still, and a retake starts from the top again.

### Setup check (milestone 4b)

**C**, offered when a project is first opened and when the input or output device changes: a line above the keys says why and names C; the check never opens by itself and never during a take. Its captures are clips of the meter's capture, never takes. Steps:

1. *Devices:* input, channel and output, as in the panel. Bluetooth output and the built-in speakers are flagged ("film sound from speakers will leak into your takes; use wired headphones"; "Bluetooth headphones add delay that can change after reconnecting; Takewise corrects it with the latency measurement (L). Wired headphones are more reliable."). The built-in output's current CoreAudio data source tells the speakers (`'ispk'`) from the headphone jack (`'hdpn'`), which is not flagged; a built-in output with neither gets the conditional "If this is the Mac's speakers, film sound will leak into your takes; use wired headphones."
2. *Voice:* the narrator reads a test sentence shown on screen. Reports peak and average speech level and any clipping, and suggests a gain change in dB on the interface so peaks land near −10 dBFS; after the narrator changes the gain, the sentence is read again until the level fits, so step 3 compares against the final gain. Hints, not verdicts: plosives (bursts of energy below 80 Hz, "turn the mic slightly off-axis or add a pop filter") and boom (much more energy below 200 Hz than in 200 Hz–4 kHz, "if you sound boomy, move a little further from the mic"; tuned on Niklas's voice at known distances).
3. *Room:* five seconds of silence. Reports the room's noise floor and the speech-to-noise ratio against step 2's speech level: 40 dB or more is good, 30–40 dB acceptable, below 30 dB noisy, with tips. Mains hum is flagged when narrow peaks at 50 or 60 Hz *and* at least two harmonics stand clearly above neighbouring frequencies for the whole recording. The recording is kept as room tone in `takes/.room/<timestamp>.wav` with a sidecar `<timestamp>.json` naming the input device, channel and output it was recorded on, its noise floor and whether it is digital silence (gated). Room tone is matched per take, never per session: for each take, `clean` uses the newest room tone recorded on the device and channel named in the take's `recorded` event, on the same local calendar day as that event (the Mac's time zone, not UTC, so an evening session keeps its room tone). The interface's gain cannot be read, so it is inferred: that room tone is used only when the take's own pre-roll noise floor is within 6 dB of the room tone's floor (a larger difference means the gain or the room changed). Otherwise, or when there is no such room tone, `clean` skips noise reduction for that take, the manifest notes it for the line, and the window suggests running the room step again.
4. *Latency:* the loopback calibration, run inside the window with the input it already holds (the same routine as `takewise calibrate`), offered whenever `[calibration]` is missing or does not match the current input, output and buffer size, including a new project, and when a remembered calibration is in use on a Bluetooth output. **L** opens this step alone at any time between takes, whatever is stored, and closes once a measurement is stored, so a Bluetooth delay that changed can be measured again on the same route after a fresh measurement too. Until it runs, takes are recorded without a latency offset and the panel says so.

Results are saved in `[setup]`.

### Remembered setup (milestone 6)

Added 2026-11-24 because every new project asked for the setup check and the loopback test again, on the same devices and the same day. Everything lives in `~/Library/Application Support/Takewise/remembered.json`, beside `settings.toml` (beside the file `TAKEWISE_SETTINGS` names, when set), with copies of room tones in `rooms/` next to it. It is changed only by one locked read-modify-write (`takewise_core::remembered`), never through `settings.toml`, which `save_defaults_to` rewrites whole. A newer version's extra fields are ignored; an unreadable file is left alone and nothing is remembered or applied until it reads again.

**Latency.**

- *Remembered:* every stored measurement (`takewise calibrate --write`, or the setup check's latency step), per exact route: input name, output name and capture buffer frames, with the offset and the date. A newer measurement replaces an older one for the same route. Opening a project also remembers its own measurement (a `[calibration]` that records its buffer size and was not itself copied) when nothing newer is remembered for its route, so the first launch of 0.2.0 already knows the WH-1000XM5 measurement of Niklas's projects (−29, −29 and −28 ms).
- *Applied:* when the window opens, and whenever the route in use or the local day changes between takes, with the devices and buffer resolved live and the input connected. If the project has no calibration that fits that route and one is remembered for exactly it, it is copied into `[input] latency_offset_ms` and `[calibration]` with `from = "remembered"` and the measurement's date. A copy is replaced the same way once a newer measurement is remembered for its route (a later day, or another offset from the same day), so measuring again in one project reaches the others; a measurement made in the project itself is never replaced. Whether the project's calibration gives way is decided from `project.toml` as it is under the project lock that writes the copy, not from what the window read earlier, so a measurement stored in the meantime (`takewise calibrate --write` beside an open window) stays. The same decision leaves the project alone when its `[input] device`, `channel` or `[output] device` are no longer the ones the window read: a project switched from Bluetooth to wired headphones in the meantime, with a measurement on them, would otherwise get the Bluetooth offset back from a window that still syncs for the old route. The store's lock is held until the project has decided (the store's lock first, the project lock inside it, as for the setup check, and never the other way round), so the measurement copied is the newest remembered at that moment and one read earlier cannot be written after a newer one has reached the project. The match is exact, so an offset is never applied to other devices or another buffer size, and it stays exact afterwards: a copied offset is used, and said to be in use, only while the output and the buffer size can be read and are the ones it was measured with. When one of them cannot be read (the interface is unplugged, say), takes are placed without the offset and `status` and the panel say so (`calibration-stale`), until the route is known again. A measurement made in the project itself is still trusted while the output or the buffer cannot be read. A project's own fitting measurement always wins; `init` copies nothing, since it knows neither the resolved output nor the buffer size.
- *Shown:* the panel and `status` (notice `calibration-remembered`) say "latency from an earlier measurement on these devices (date)". Remembered offsets apply to Bluetooth outputs too. For a Bluetooth output the panel adds "Bluetooth delay can change after reconnecting; press L to measure it again (15 s) if takes sound late." to any calibration in use, a copied one and one measured in the project alike (the headphones can reconnect after either), L opens the latency step alone, and for a copied one the setup check (C) also offers its latency step although the calibration fits. `doctor` keeps warning that wired headphones are better.

**Setup check.**

- *Remembered:* after each setup check, its `[setup]` result for its exact input, channel and output, with a copy of its room tone (WAV and sidecar) in `rooms/`. Results and room tones from earlier days are pruned: the new room tone is copied first and synced with its folder, `remembered.json` is committed (written, renamed over, and its folder synced), and only then, still under the store's lock, are the room tones removed that it no longer names. A write or a sync that fails in between leaves the file as it was, with every room tone it names, and so does a power loss at any point.
- *Adopted:* a project with no `[setup]` from today (local day) for the route in use adopts the result remembered from today for exactly that input, channel and output: the room tone is copied into its own `takes/.room/` first (once; a copy it already holds is not copied again), then `[setup]` is written with `from = "remembered"`. Whether the project still lacks today's check is decided from `project.toml` as it is under the project lock, before the room tone is copied in, not from what the window read earlier, so a check that ran in the project in the meantime stays. A project whose `[input] device`, `channel` or `[output] device` are no longer the ones the window read adopts nothing either. `clean` and the setup offer then work unchanged, from the project's own files; a take whose pre-roll floor differs from the room tone by more than 6 dB still skips noise reduction, and the window still suggests the room step again.

**Noise per take.** `checked` gains `speech_level_dbfs` (RMS over the energy speech range). A new verdict rule between rules 7 and 8 (after the sound rule, before `keep`): a take whose speech-to-noise ratio (speech level against its own pre-roll floor) is below 30 dB gives `listen` ("background noise only 24 dB below your voice"). An absolute floor is not used, because it depends on gain.

**Cleaner audio for the checks.** Before transcription, the take is converted with a high-pass at 60 Hz and its peak normalized to −3 dBFS (no loudness normalization), so rumble and a quiet take do not confuse Whisper. The take file is never changed. The `checker` string's preprocessing tag changes from `pre=none` to `pre=hp60+norm`, so takes checked before are transcribed again. The high-pass is lower than the export's 80 Hz on evidence: at 80 Hz and at 100 Hz, Whisper heard "build" for "built" in one of the eight Kindred lines; at 60 Hz, as without a filter, all eight stay `keep`.

### Export cleanup and formats (milestone 4b)

Takes are always recorded as 48 kHz, 24-bit WAV, the lossless original, and are never modified. Export follows `[export]`, overridable with `takewise export --format … --bit-depth … --sample-rate … --processing …`. The file is `export/narration.wav` or `export/narration.flac`.

`clean` works in this order, all at 48 kHz until the last step:

1. Each used take, whole, through a high-pass at 80 Hz and gentle noise reduction (`afftdn`, fixed reduction of 10 dB, noise floor from the take's own room tone, matched as described in the setup check's room step: the newest one on the devices and the day of the take's `recorded` event, used only when the take's pre-roll noise floor lies within 6 dB of its floor). Noise reduction is skipped for a take without such a room tone, or whose room tone is digital silence (a gated interface); the manifest notes each take it skipped and why, in the line's `noise_reduction` and as a `noise-reduction-skipped` warning. A seam run (see "Export and Resolve handoff") is cleaned as one file, so no filter starts anew at a cut; its room tone is matched once, by its first take's `recorded` event and the passage's noise floor, and noted on each of its lines. A click fixture proves the filters add no delay, or the delay is measured and compensated, so `clean` places speech exactly where `raw` does. Measured with `ffmpeg` 8.1: the high-pass keeps a click on its sample; `afftdn` delays its output by 1200 samples (25 ms) and drops as much at the end, so each export measures that delay with a click and compensates it (padding the end, trimming the start). On the Kindred lines, a click put into a take lands on the same sample in `raw` and `clean`, and the speech of all eight lines lines up at lag 0 above 1 kHz (below that, the high-pass's phase shift makes speech look a few samples early to a cross-correlation without moving it).
2. Placement, fades and cropping in Rust, as for `raw`.
3. Loudness: measure integrated loudness and true peak of the assembled narration (`ebur128`), apply the static gain to reach −16 LUFS, and pass the result through a transparent look-ahead peak limiter (`ffmpeg`'s `alimiter`: 5 ms look-ahead and attack, 80 ms release, no auto level) run at 4× the sample rate between two `swr` resamplings, so it catches the peaks between samples that the true-peak meter sees. Its ceiling is −1.5 dBFS at 4× oversampling, which leaves 0.5 dB for resampling and dither below the −1 dBTP limit. The limiter takes some loudness, so the narration is measured again and the gain corrected, until it lies within 0.1 LU of −16 LUFS (at most five passes). The limiter never reduces the gain by more than 6 dB: the gain stops where it would, the narration stays below −16 LUFS, and the manifest records the shortfall (`loudness_target_reached: false` and a `loudness-target-missed` warning) beside the largest reduction applied (`limiter_max_reduction_db`). The limiter's delay is measured with a click, as for the noise reduction, and compensated (with `latency=1`, `ffmpeg` 8.1 measures 0 samples). This replaces the earlier rule of one static gain capped by the true peak, with no dynamic processing, which left Niklas's Kindred lines (peaks about 16 dB above their average level) at −19.1 LUFS, −1.1 dBTP; with the limiter they export at −16.0 LUFS, −1.5 dBTP (−1.4 at 44.1 kHz, 16 bits), with at most 4.2 dB of gain reduction. See the decision record "Reach the loudness target with a look-ahead peak limiter".
4. Resampling to 44.1 kHz (once, for the whole narration, with `ffmpeg`'s own resampler `swr` and a 128-tap filter, since Homebrew's `ffmpeg` is built without `soxr`) and triangular (TPDF) dither of ±1 LSB from a fixed seed when writing 16-bit, done in Rust so an export is reproducible.
5. Verification: integrated loudness and true peak are measured again on the final encoded file and recorded in the manifest. If resampling or dither pushed the true peak above −1 dBTP, the gain is lowered by the excess and steps 3–5 run once more; the manifest records the final values.

`raw` skips steps 1 and 3 and needs no `ffmpeg` unless resampling or FLAC is requested (16-bit WAV at 48 kHz is dithered in Rust and needs none either); `doctor` checks `ffmpeg`. `takewise init` writes `[export]` with `processing = "clean"`; a project without `[export]` stays `raw`. The manifest also records the static gain (`gain_db`) and, per line, the noise reduction a take got or why it was skipped (`noise_reduction`). The manifest states `sample_rate` of the export file and `source_sample_rate` (48000) of the takes: source ranges stay in take samples at 48 kHz, destination ranges are in export samples (`round(n × rate / 48000)`), and film seconds are authoritative.

## Passages

Added 2026-11-24 (milestone 6, see `docs/plans/2026-11-24-m6-passages-and-remembered-setup.md`). Sentences that run into each other lose their flow when each is read as a take of its own. A passage is read in one go and still picked up line by line.

**What a passage is.** A run of consecutive lines in which each line's slot ends less than `[record] passage_gap_s` (1.0 s) before the next line starts: `next.start − slot_end(k) < passage_gap_s`, where the slot end is the line's `end`, or else the next line's start. Scripts whose sentences lie 0.1 to 0.7 s apart and whose pauses for picture or music last 1.4 s or more are grouped without any change. `status --json` gives each line its `passage`, the id of the passage's first line.

**On disk.** The capture of a passage is one file, `takes/.passages/<uuid>.wav`, written and published as "Writing files safely" describes. Its sidecar `<uuid>.json` has a schema of its own, marked `"kind": "passage"`, so it is never read as a take's metadata: the `id`, the `lines` (each line's id and its snapshot when the take started), `sample_rate`, `device`, `channel`, `latency` (`input_s`, `offset_ms`: what the samples were placed with), `preroll_s`, `first_sample_film_s` (the film time of the first sample; absent until the sample is placed), `dropouts` (each gap's `at_sample` and `missing`), `film_shift_ms`, and, once the take is stopped, `samples`, `preroll_floor_dbfs` and the `cuts`, each `{ sample, cue_film_s, pause }`.

**Cutting.** Each line whose start the capture reached gets one piece; the pieces are contiguous and cover the passage exactly, piece *i* being line *i*'s. Times become sample positions through `first_sample_film_s`, the mapping that places takes. For the boundary between line *k* and line *k+1*:

1. The search window runs from the midpoint of line *k*'s slot to the midpoint of line *k+1*'s, clamped to the captured range. A slot that runs past the next line's start (overlapping slots) counts only up to that start, so the windows follow each other in the lines' order, each around its own cue, and two boundaries never search the same audio. A window also begins after the cut before it; a boundary left without audio that way (two lines that start on the same sample) ends the cutting, and the lines from there on get no take.
2. Pauses are runs of 10 ms frames, inside the window, at or below the energy detector's speech threshold, which comes from the noise floor of the passage's pre-roll.
3. The cut is the middle of the first of these that exists: the pause that contains the cue gap (from line *k*'s slot end to line *k+1*'s start), or else the cue (line *k+1*'s start), if it lasts at least 150 ms; the longest pause of at least 150 ms within 1 s of the cue; the nearest pause of at least 80 ms in the window (a stop closure inside a word is shorter). Without any, the cut is the cue itself (or the end of the window nearest to it) and is marked `pause: false`. Every cut lies in its own window, and `pause` says whether that very sample lies in a pause.
4. A trailing piece without speech (the take was stopped right after a line began, or the last lines were never read) joins the piece before it, and its line gets no take. A line cut off mid-word keeps its piece, and its words check says what is missing.

**Pieces are ordinary takes.** Each piece is written as `takes/<line>/NNN.wav` with its `NNN.json` and a `recorded` event. Its `line_offset_s` comes from its first sample and the line's start when the take began, its `dropouts` counts the passage's gaps that fall into it, and its `passage` object (see "The ledger") says which piece of which passage it is. Everything that works on takes works on pieces: checks, judgments, ranking, choosing, export. Export joins the pieces chosen for consecutive lines again, so a passage chosen whole is exported as it was recorded (see "Export and Resolve handoff").

**Checks on a piece.** The noise floor is `passage.preroll_floor_dbfs`, not the piece's own first seconds, which are speech; the speech threshold, the noise rule and room-tone matching all use it. The timing rule moves to the passage's edges: overrun counts only on the last piece and early start only on the first. In its place, after rule 4: a piece after the first whose words start more than 1.0 s from its line's start, in either direction, gives `listen` with `passage-drift` ("started 1.4 s before its cue"), and both pieces beside a cut with `pause: false` give `listen` with `passage-boundary` ("no pause found at the boundary with the next line; the words may be split between lines"). No speech, clipping and missing or extra words still come first. Ranking is unchanged.

**Choosing a passage.** `takewise choose <dir> --passage <id>` chooses that passage's take for every line that has one, so the passage is used whole: under the lock it checks that every piece has its take and each take's file exists, then adds all the `chosen` events at once: a copy of `takes.jsonl` with every byte it has followed by the events is fsynced and renamed over it, so a failure or a crash on the way leaves either all of the choices or none, never the first few lines of the passage. Lines without a piece keep their choice. **Shift+Enter** in the window does the same for the selected take's passage and says how many lines it chose.

**Recording one in the window.** **Shift+Space** records from the current line through the end of its passage; Space and R still record the current line alone, and Space or Shift+Space stops any take. With one line left in the passage it is a take of that line.

- One capture and one film playback, with the clock, latency offset and timebase history of a line take. Pre-roll and count-in come only before the first line. The take stops `tail_s` after the last line's slot (or the film's end), or on a capture failure.
- The lines are snapshotted when the take starts, so **M** is off during a passage take (it stays on during a take of one line).
- The prompter follows the film: the recorder tracks the line being read by its snapshot, and line *k+1* becomes current when the film reaches its start, with its text, pace fill, note and next line (after the last line, the line that follows the passage). The prompter's scroll starts at the top at each switch. For `PASSED_S` (1.5 s) of film after a switch, line *k* stays in view above line *k+1*, dimmed on one row and ellipsized, so a narrator who runs a little late can finish it; line *k+1*'s pace fill still starts at its cue. The row is reserved, empty, for the whole passage take (it appears with the pre-roll), so the line being read never moves when the row fills or empties. Delaying the switch past the cue was the alternative; it was rejected because a narrator on time would then start line *k+1* without seeing it. The line list marks the line being read, and the window's current line follows it. When the narrator stops the take (or the capture fails), the current line stays on the line being read, so Shift+Space picks the passage up again from there; when the take runs to its end, the current line goes back to the line the take started on, so Shift+Space reads the whole passage again.
- The sidecar is written once the film is scheduled and the first sample placed, and written again when the film's timebase, as read back, moves that sample (a late start), so a passage a crash interrupts is cut where it was recorded.
- On stop, the passage is published in the frame (finish, cut, the two renames). `split` then runs on a worker thread, which also measures each take's peak for the "clipped" mark; the window keeps the audio's lock until the takes are there and then reloads. Closing the window waits for it.
- A passage that cannot be published stays in memory with its lock and is retried every two seconds, like a take; a published one whose cut failed is cut again, and by any repair.

**Hearing one.** **Shift+P** plays the selected take's passage, the passage file locked to the film, to the passage's end. From the first piece it plays from the passage's own first sample; from a later piece the film starts `preroll_s` before that piece's line as recorded (or before the piece, if it begins earlier) and the passage file plays from the sample the film starts at, so the narrator hears a line read inside the passage with the end of the line before. **P** still plays one take in context, and plays a piece through its own end and `tail_s`: a piece ends at the cut before the next line, which can lie past its slot's tail, and a slot shortened after the recording can even end before the piece begins. When a take's first sample lies after the point the film starts from (any piece but the first), the take is scheduled at its own host time, from its beginning, instead of at a negative offset.

## Distribution

Added 2026-11-23 after council round 5.

- **Install:** a Homebrew cask in Niklas's tap (`niklas-heer/tap/takewise`) installs the Developer ID signed and notarized `Takewise.app` and links its `takewise` binary onto PATH (`binary` stanza). The cask depends on the `whisper-cpp` and `ffmpeg` formulae. Without Homebrew, the app's menu offers "Install Command Line Tool", which links `~/.local/bin/takewise` to the binary inside the bundle (as Focal does).
- **Without the tools:** recording, choosing and `raw` WAV export at 48 kHz work without `whisper-cli` and `ffmpeg`; checks then give `listen` with `words-not-checked`, and `doctor` and the window say how to install them. Such a take is checked again only when that could end differently: once the tools and model are set up, when the setup now fails for another reason, or when the transcription timed out; a check that fails exactly like the take's newest one is reported without appending another `checked` event. Like the fold, the selection reads a take's newest check against the line as it is now, so a failed recheck after a successful one is not hidden from later batch checks.
- **The speech model:** not bundled (1.5 GB). On first launch, and whenever it is missing, the window shows "Install the speech model (1.5 GB)"; `takewise models install` does the same from the command line. Both download `ggml-large-v3-turbo.bin` from the whisper.cpp model repository on Hugging Face into `~/.local/share/takewise/models`, show progress, verify its SHA-256 against a value pinned in the source, and resume an interrupted download. Until it is installed, checks run without words.
- **Microphone permission** belongs to `Takewise.app`; macOS asks the first time the window opens the input, which its meters do as soon as an input is chosen: on a first project when the narrator picks it in the audio panel, on a project whose input is already set when the window opens. `doctor` and the window explain how to grant it in System Settings when it was denied; the window then does not record. Since a process started from a terminal gets the terminal's permission, `doctor` asks `Takewise.app` itself (started in the background with `open`, without a window or a prompt).
- **Docs:** the README covers install, a first session, the keys, the Resolve recipe and agent use; `AGENTS.md` in the repo covers contributors. A short agent guide (`docs/agents.md`) shows an agent's full loop: `init`, writing `script.toml`, `status --json`, `check`, `judge`, `choose`, `export`, and placing the result in Resolve.
